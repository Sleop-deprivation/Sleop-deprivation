The Process

Humble beginnings

Finding the move was simple. The URL was just the regular API name followed by the move, with a bit of formatting needed to get the search to run. Namely, the search must be fully lowercase, and any spaces must be replaced with hyphens. This was very easy to convert since all relevant move names have no more than one space and none have hyphens. However, PokeAPI's contest effects aren't listed in the move itself, but rather in a seperate link, since some moves share contest effects. This was the first of many times that nested GET calls were to be used, since after getting a move, I'd need to make a seperate call to get its effects. Additionally, moves used in Contests (from Gen 3, the GBA games) and Super Contests (from Gen 4, the first DS games) have completely different effects and mechanics between them, as well as different API links, and since I wanted to include both versions of contests, splitting up otherwise identical code into an if statement was a necessity.

I think people who design APIs actually hate web developers

The next challenge came in filtering by Pokemon. PokeAPI does return a Pokemon's moveset as part of the Pokemon data, but it returns the API links to those moves, so getting their data required a nested API call which itself contained a nested API call. That wasn't too big of a deal for individual moves, but one could get returned many seperate moves on a given Pokemon, and the amount of calls would add up rapidly. So I decided to be a bit sneaky and make a couple of bonus calls on-load. Firstly, a list of every move's name that can be learned in Gen 4 is called from PokeAPI, and filtered to include only moves available in Gen 3 for use in a separate list. However, the true sneakiness comes in me making an additional few calls to Bulbapedia via MediaWiki's API. PokeAPI doesn't have a full list of moves by contest type, and making 400+ calls on-load didn't sound ideal. Bulbapedia did have such a list, however, on each type's respective page. Unfortunately, MediaWiki's API is not good, and the text returned through a parse is all of the site's HTML data, which is awful to sort through. My workaround was to get a list of every link on that page, since the moves were directly linked to, filter that list to only include links that were names of moves (using my previously-initialized move list), and store each list of moves by type in their own list. That way, I can reduce the amount of API calls from 50+ when loading the moves to only one when selecting a move returned from the results.

Additional proof that API designers have it out for us

Unfortunately, that came with an additional problem. Some moves changed contest types between Gen 4 and Gen 6 (the 3DS games, and the next appearance of contests). While PokeAPI doesn't have Gen 6 contest data, Bulbapedia does, and some moves were added to two move type lists, since Bulbapedia had linked to them on two contest type lists. This wasn't a problem when finding a single move, since PokeAPI only has pre-Gen 6 contest data, but became very evident once I color-coded search results and found moves of different colors and different types appearing where they shouldn't. This was a big enough issue to warrant a big enough fix. So what I did is that, instead of throwing in the towel and just making 100+ API calls on-load, I learned how to use regular expressions so that I could more easily get a list of every instance of a move or its types being called. The way the list of moves on Bulbapedia looked was Move | Original Type | New Type, and each link's title was "Name (property), so for every instance of a move link found, the following two links would be the move's original and new type. With the filter made and the hard part out of the way, I removed every instance of the move in the New Type's array, and spent a total of three hours bugfixing a problem that I wouldn't have had to fix if APIs were simply better. I love coding.

That was actually the last of my problems

After that, it was pretty smooth sailing. The rest of the more specific functions required substantially less code and thought, to the point where about 75% of my expected functionality was available for the in-class feedback session, and none of the following issues were far less annoying and far less noteworthy. It was primarily making the site look better, adding some quick and easy proposed features from the feedback session, and feeling relieved that I actually scoped properly this time. So at the end of the day, I'd call this site a pretty big success.
